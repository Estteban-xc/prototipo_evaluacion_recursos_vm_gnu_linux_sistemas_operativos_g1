¿Qué estamos evaluando?

Observamos recursos de una VM GNU/Linux y usamos Python 3 para servir temporalmente este portal en localhost. También comparamos el sistema con el servicio de descubrimiento de impresoras de red cups-browsed activo y detenido temporalmente. No se modifica el kernel ni se deshabilita el servicio de forma permanente.

Procedimiento de la demostración

  1. Registrar los recursos de la VM en entorno_vm/configuracion_vm.csv y tomar la medición inicial con el servidor detenido.
  2. Desde la raíz del repositorio, iniciar el servidor temporal ligado a 127.0.0.1.
  3. Comprobar el portal y sus enlaces desde la propia VM.
  4. Registrar memoria con el servidor web detenido y activo, e identificar el proceso Python.
  5. Comparar cups-browsed activo y detenido temporalmente, sin deshabilitarlo al inicio.
  6. Restaurar el servicio y describir los resultados sin generalizarlos a otros equipos.

Resultados preliminares

En Ubuntu 26.10 instalado persistentemente, una petición local respondió HTTP 200 y el tiempo de arranque registrado fue 17,831 s. El proceso del portal Python presentó RSS de 23 360 KB, 22 496 KB y 22 504 KB en las lecturas compartidas.

Para cups-browsed, tres lecturas con el servicio activo mostraron 1097 MiB disponibles y 13 934 592 bytes reportados por MemoryCurrent. Tras detenerlo temporalmente, tres lecturas mostraron 1099 MiB disponibles y MemoryCurrent no establecido. El servicio se reinició y se confirmó activo y habilitado. La diferencia observada fue de 2 MiB disponibles; es modesta y corresponde únicamente a esta VM, sin demostrar una mejora general.

Límites y seguridad

El servidor es temporal y solo escucha en la propia VM. Sirve los archivos del repositorio a localhost; por eso no se deben guardar allí credenciales ni datos personales. No es un sitio público ni un servidor para producción. No usar 0.0.0.0 ni reenviar puertos. Al finalizar, detenerlo con Ctrl+C.
